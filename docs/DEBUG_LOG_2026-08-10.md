## 1. Release APK "Unable to connect to server" despite a healthy backend

**Symptom:** the signed release APK failed every API call with a generic
"Unable to connect to server" banner on login, even though
`https://api.rutec.my/api/auth/login` worked perfectly from curl/Postman and
the correct URL was confirmed compiled into the JS bundle.

**Root cause:** switching `capacitor.config.ts`'s `androidScheme` from the
default `capacitor` to `https` (done as part of Play Store production
hardening) changes the WebView's **origin** from `capacitor://localhost` to
`https://localhost`. The CORS allowlist in `server.js` only listed
`capacitor://localhost` and `http://localhost` — not `https://localhost` — so
every preflight was rejected before the request ever logged anything
server-side. From the API's point of view nothing was wrong; the request never
arrived.

**Why it was hard to spot from the backend alone:** a blocked CORS preflight
never reaches Express — there's nothing to see in server logs, `errorResponse`
output, or even `adb logcat` (Capacitor doesn't forward WebView console/network
errors to logcat by default). It only shows up in the **browser's own console**.

**How to diagnose this class of bug:**
1. Confirm the backend is healthy independently (curl the exact endpoint with
   real credentials).
2. Rule out signing/network-config/DNS/SSL cert (SAN vs CN, wildcard coverage)
   before suspecting CORS — but if those are all fine and it's *still* failing
   only from the native app, suspect CORS next.
3. Use `chrome://inspect#devices` (Chrome on the same PC, phone connected via
   USB with Developer Options + USB debugging on) to open live DevTools against
   the app's WebView. The **Console** tab shows the exact CORS error immediately:
   `Access to fetch at '...' from origin 'https://localhost' has been blocked by
   CORS policy: ... No 'Access-Control-Allow-Origin' header ...`.
   - Release builds don't expose a debug socket by default. Temporarily add
     `WebView.setWebContentsDebuggingEnabled(true)` in `MainActivity`'s
     `onCreate` to enable it, rebuild, and remove it again once done — see the
     frontend debug log `DEBUG_LOG_2026-08-10.md` for the exact change and full
     `chrome://inspect` walkthrough.
4. Once the exact blocked origin is known, add it to the `corsOptions.origin`
   array in `server.js` (production branch only) and redeploy.

**Fix:** add `"https://localhost"` alongside the existing `"capacitor://localhost"`
/ `"http://localhost"` entries. Whenever `androidScheme` changes in
`capacitor.config.ts`, the CORS allowlist here must be checked/updated to match.

**Verify the fix is live** without touching the app:
```sh
curl -s -i -X OPTIONS "https://api.rutec.my/api/auth/login" \
  -H "Origin: https://localhost" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: Content-Type"
# Look for: Access-Control-Allow-Origin: https://localhost
```

## 2. CI `npm ci` fails with Puppeteer `ECONNRESET` / Chromium download error

**Symptom:** `.github/workflows/ci.yml`'s `npm ci` step fails with
`Failed to set up chrome-headless-shell ... ECONNRESET`, even though nothing
related to Puppeteer changed.

**Root cause:** the `puppeteer` package's postinstall script downloads its own
bundled Chromium/`chrome-headless-shell` binary from Google's CDN. This
download is flaky on GitHub-hosted runners and unnecessary here — production
uses `puppeteer-core` + `@sparticuz/chromium` exclusively (see
`DEBUG_LOG_2026-08-04.md` §4), and the CI test job doesn't exercise PDF
generation at all. `puppeteer` (full package, not `-core`) is only present as
a local-dev convenience fallback in `utils/browserHelper.js` /
`utils/puppeteerBrowser.js`.

**Fix:** set `PUPPETEER_SKIP_DOWNLOAD: true` as an env var on the `npm ci` step
in `ci.yml`. The Dockerfile already had the equivalent
(`PUPPETEER_SKIP_CHROMIUM_DOWNLOAD=true`) for production builds — `ci.yml`'s
bare `npm ci` was the one place this guard was missing.
