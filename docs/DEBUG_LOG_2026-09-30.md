## 1. Staging KTA association showing 0 bookings/companies while NTA showed inflated numbers

**Symptom:** on staging (`staging.rutec.my/admin/association-stats`), KTA
(Kiulu Tourism Association — the entire target of the Kiulu legacy migration
covered in `docs/LEGACY_DB_MIGRATION_ANALYSIS.md`) showed 0 bookings, 0
companies, RM 0 revenue, while NTA (Nabalu Tourism Association, a small
unrelated association) showed implausibly large numbers (1,049 tourists,
RM 1,105,438.00 revenue).

**Initial (wrong) hypothesis:** `services/dashboardService.js` resolves a
company's association via `MIN(association_id)` across its users (3
occurrences in that file). Since association ids are KOBETA=1, RATA=2,
KOMTDA=3, USTA=4, NTA=5, KATA=6, **KTA=7** (the highest id of all 7), any
company with users split across two associations would always lose the
`MIN()` race to a lower-numbered association — meaning KTA is structurally
guaranteed to never win that comparison if even one collision exists. The
suspected mechanism was `seeders/20260915000002-seed-legacy-companies.js`'s
company-matching query (`WHERE company_name = :name LIMIT 1`, no association
scoping) silently merging a new KTA company into a pre-existing same-named
company in another association.

**Actual root cause (confirmed via staging SQL dump analysis):** the Kiulu
migration seeders had **never actually run on staging at all**. Diagnostic
evidence, from parsing `dump-rural_tourism_staging-202609171712.sql` directly
(no `mysql` client/Docker available in-session, so parsed the dump text with a
Python port of the same bracket/quote-aware INSERT tokenizer used throughout
the original migration analysis):
- Zero companies had users spanning multiple `association_id` values (directly
  contradicting the split-association hypothesis).
- Staging's `users` table had only **1** user with `association_id = 7`
  (KTA) — `kta@ruraltourismsabah.com`, `company_id = NULL` — a pre-existing
  placeholder admin account, not any of the 54 migrated Kiulu users.
- Staging's `companies` table had only 45 rows total (expected ~82 if the
  baseline + 37 migrated companies were both present).
- The `legacy_id_map` table (created by
  `seeders/20260915000001-seed-legacy-id-map-table.js`, step 1 of the
  migration) **did not exist at all** on staging.
- The `legacy_receipt_id` column *did* exist on `bookings`, and
  `SequelizeMeta` recorded the `20260915000000-add-legacy-receipt-id-to-
  bookings` migration as applied.

**Conclusion:** the schema migration (`npm run db:migrate`) had been run on
staging, but the seed step (`npm run db:seed`) never was. KTA showed 0 because
it genuinely had no migrated data there — not because of any company/
association merging bug. NTA's numbers were not necessarily wrong either;
nothing in the (absent) migration data could have leaked into NTA's real
pre-existing figures.

**Fix:** operational, not code — run `npm run db:seed` on staging (and
confirm on production before assuming it's already there). No code changes
were required for this specific incident; the `MIN(association_id)` pattern
remains a latent risk worth revisiting separately if a genuine multi-
association company is ever found (none currently exist).

**How to diagnose this class of bug without DB access:** when `mysql`/Docker
aren't available in the working environment, a raw `.sql` dump can be parsed
directly in Python: locate the `INSERT INTO \`table\` VALUES (...), (...);`
statement, and walk it character-by-character tracking quote state (respecting
backslash escapes and doubled `''` sequences) and paren depth, splitting on
commas only at depth 1 and rows only at depth 0. This mirrors
`scripts/parseLegacyDump.js`'s row parser. Gotcha: dump files may use CRLF
(`\r\n`) line endings — don't terminate on `;\n"`, terminate on any depth-0
`;` instead.

## 2. Product-picker bug: bookings could silently resolve to another company's product

**Symptom:** an operator (Justin Ranny, migrated KTA user, company "Kiulu
Eco-Tourism") selected "Kayak" from his own company's activity dropdown, but
the resulting booking landed in the frontend's Sync Conflict screen with
`403 Forbidden. You can only process bookings for products in your own
company.`

**Root cause:** `services/productService.js`'s `getAllProductsByLocation()`
(backing `GET /api/products/shared-by-location`) returns products from
**every company sharing the same `Company.location` string**, not just the
caller's own company. The frontend's activity/accommodation booking form
(`rural-tourism-frontend`'s `booking-add.page.ts`) used this location-wide
endpoint to re-resolve a typed/selected product **name** back into a
`product_id` at submit time (`findProductByName()`), rather than the
company-scoped endpoint the dropdown itself was built from. Because "Kayak"
is not a unique name — another company at the same location also has its own
product named "Kayak" — the lookup could resolve to the wrong company's
product id.

**Why this disproportionately affects migrated Kiulu/KTA accounts:** all 37
migrated companies share the literal `location: 'Kiulu'` value (a migration-
time limitation — the old system had no real address data). This merges all
37 companies into one shared, collision-prone pool for `shared-by-location`
queries. A direct check of the 37 migrated companies' product names found
**47 duplicate names** among them alone (e.g. "hiking" appears in 27
different companies, "kayak" in 5, "rafting" in 4). Pre-existing, non-
migrated companies have real, distinct addresses, so their location-scoped
pool is naturally much smaller and far less likely to collide.

**Fix:** this was a frontend-only fix (see the frontend debug log's §1 for
the exact change to `findProductByName()` — it now calls
`getProductsByCompany(companyId)` first instead of `getProductsByLocation()`).
No backend change was needed; `services/productController.js`'s
`validateProductAccess()` (which threw the 403) was already working exactly
as designed — it's the correct safety net that caught this bug before it
could corrupt a booking's company attribution, rather than a bug itself.

**Verify:** create a booking for a product name that's duplicated across two
companies at the same location; confirm the resulting `product_id` belongs to
the booking operator's own company (`SELECT company_id FROM products WHERE
id = :product_id` should equal the booking user's `company_id`).

**Recurrence in a second frontend entry point, same day:** the identical
symptom reproduced again — Sync Conflict screen, `Forbidden. You can only
process bookings for products in your own company.`, this time via the app's
E-Receipt (walk-in) booking form rather than the offline booking form
originally diagnosed. Confirmed via direct DB lookup that the offending
`product_id` (27, "Kayak") belonged to a different company (id 63, "Dapako
Hill - Lingga Eco Tourism") than the booking operator's own company (id 59).
Root cause and fix were entirely frontend-side (a second, independently
copy-pasted `findProductByName()` in `ereceipt-add.page.ts` that the original
fix never touched) — see the frontend debug log's §1 recurrence note for the
full detail and the follow-up whole-codebase audit that confirmed no further
copies of this bug remain anywhere in the app.

**Backend diagnostic notes from tracing this recurrence** (no backend code
changed, but useful for the next time this class of bug is investigated):
- `controllers/bookingController.js`'s `getBookingById` throws a **403** via
  `policy("booking", req.user, booking).show()` →
  `policies/bookingPolicy.js`'s `show()` → `_sameCompany()`, which requires
  the booking's own `company_id` to exactly equal the caller's
  `req.user.company_id` (or, for package bookings, match one of the
  package's `referee_id`/`referrer_id` companies). This is the same
  `company_id` mismatch mechanism as the original incident — a different
  code path (`getBookingById`'s policy check) catching the same underlying
  wrong-`product_id`-at-creation bug, not a separate authorization bug.
- Passing a non-numeric id (e.g. the offline-queue's local UUID) to
  `services/bookingsService.js`'s `getBookingById(id)` throws a clean
  **400** ("Invalid booking id"), not a 403 — worth ruling this out
  explicitly early when a "permission" toast appears for what looks like an
  id-format issue, since the frontend's global HTTP interceptor
  (`http-interceptor.service.ts`) rewrites **every** 403 response to the
  generic message `"You do not have permission to perform this action."`
  regardless of which endpoint or policy actually produced it — the toast
  text alone cannot distinguish "real ownership mismatch" from any other
  403 source without checking the network request itself.

## 3. `Unexpected end of form` leaking as a raw 500 on interrupted operator registration uploads

**Symptom:** operator self-registration (`POST /api/auth/register`, a
`multipart/form-data` request with up to 4 optional file uploads via
`upload.fields(...)` in `middleware/uploadLogo.js`) intermittently failed with
a raw `"Unexpected end of form"` message surfaced directly to the user,
alongside a generic "Server error. Please try again later." toast.

**Root cause:** `"Unexpected end of form"` is Busboy's (Multer's underlying
multipart parser) exact error string when the request body stream ends before
the closing multipart boundary is received — i.e. the upload was interrupted
mid-transfer (weak/unstable connection, proxy timeout, etc.), not a
client-side bug. `server.js`'s central error handler special-cased only
`multer.MulterError` with `code === "LIMIT_FILE_SIZE"` (→ 413); this plain
`Error` fell through to the generic `res.status(err.status || 500).json({
message: err.message })` branch, which has no `.status` set on this error, so
it became a 500 with the raw parser string as the user-facing message.

**Fix:** added a specific catch in `server.js`'s error-handling middleware,
immediately after the existing `LIMIT_FILE_SIZE` check:
```js
if (err.message === "Unexpected end of form") {
  return res.status(400).json({
    success: false,
    message: "Upload was interrupted. Please check your connection and try again.",
  });
}
```
This doesn't fix the underlying network interruption (nothing server-side
can), but replaces a confusing internal parser error with an actionable
message and a semantically correct 400 instead of 500. Purely additive — no
frontend changes needed, since the frontend already just displays whatever
`error.error.message` the backend returns.

## 4. Deactivated user accounts could still log in (feature built, then found broken on first real test)

**Context:** built a soft-deactivation feature for both `products`
(Master Data) and `users` (User Management) — see the "Features built this
session" section below for the full list. Immediately after building the
`is_active` login gate for user accounts, the very first real end-to-end test
(deactivate an account, log out, log back in with its real credentials)
showed the account could **still log in**.

**Root cause:** operator/staff accounts (`unifiedUserModel.js`, the `users`
table backing the whole User Management feature) authenticate through a
**separate code path** —
`authService.loginFromUnifiedUsers()` — which is entirely distinct from the
`resolvers` loop where the `is_active` check was first added (that loop only
handles `tourist` logins and a legacy `association_users`-table login; it
never runs for unified-user accounts at all, because
`loginFromUnifiedUsers()` returns early at the top of `login()` before the
resolvers loop is ever reached). The initial fix
(`assertAccountIsLoginEligible()`, extended to cover `USER_TYPE_OPERATOR`/
`USER_TYPE_ASSOCIATION`) was correctly written but call-site-unreachable for
the exact account type the feature was built for.

**Why it wasn't caught immediately:** the code compiled and ran without
error; the eligibility check itself was correct in isolation (confirmed via a
throwaway Node script calling `authService.login()` with a wrong password,
which correctly still rejected on `401` — that test exercised the wrong code
path and gave false confidence). Only a real end-to-end login attempt with
valid credentials against the actual `loginFromUnifiedUsers()` path surfaced
the gap.

**Fix:** added the `is_active === false` check directly inside
`loginFromUnifiedUsers()`, immediately after password verification and before
role/token resolution:
```js
if (user.is_active === false) {
  const error = new Error(
    "Your account has been deactivated. Please contact your association or admin.",
  );
  error.statusCode = 403;
  throw error;
}
```
The earlier `assertAccountIsLoginEligible()` extension was left in place
(harmless — it's dead code for `association_users`-table logins, which have
no `is_active` column at all, so the check is always a no-op pass-through
there) rather than removed, since removing it risked re-introducing the gap
if a future refactor ever merges the two login paths.

**Verify:** toggle a user's `is_active` off via Master Data → User
Management's Status toggle, log out, attempt to log back in with that
account's real credentials — expect a 403 with the message above, not a
successful login.

## Features built this session (backend side)

**Product soft-deactivation (`is_active` on `products`):**
- `migrations/20260929151750-add-is-active-to-products.js` — adds
  `is_active BOOLEAN NOT NULL DEFAULT true`.
- `models/productModel.js`, `serializers/productSerializer.js` — expose the
  field.
- `services/productService.js` — `getAllProducts`/`getAllProductsByCompany`
  accept an `includeInactive` flag (default `false` = active-only);
  `getAllProductsByLocation` is **always** active-only (it only ever feeds
  booking pickers, never master-data management); `updateProduct` accepts
  `is_active` in its update payload.
- `controllers/productController.js` — the master-data list endpoints
  (`/api/products`, both superadmin and per-company paths) pass
  `includeInactive: true`; the booking-picker endpoint
  (`/api/products/company/:companyId`) intentionally does not, so deactivated
  products silently disappear from booking forms without any frontend
  filtering logic needed.

**User soft-deactivation + role management (`is_active` on `users`, plus
letting `operator_admin` choose roles):**
- `migrations/20260929153741-add-is-active-to-users.js` — same pattern as
  products.
- `models/unifiedUserModel.js`, `serializers/userSerializer.js` — expose the
  field.
- `services/authService.js` — login gate, see §4 above.
- `services/userService.js` — `_buildUserFields` accepts `is_active`;
  `getOperatorAdminRoleId()` / `getOperatorRoleIdByName(name)` added
  (restricting non-superadmin role assignment to exactly `operator_admin` /
  `operator_staff` — nothing else is reachable through this path, closing off
  any risk of a non-superadmin granting themselves or anyone else a
  superadmin/association role).
- `controllers/userController.js`:
  - `createUser`: a non-superadmin (`operator_admin`) caller can now pass
    `role: "operator_admin" | "operator_staff"` when adding a new user for
    their own company, instead of being hardcoded to `operator_staff`. Real
    motivating scenario: an operator_admin adding a spouse/co-owner as a
    second admin, so the company isn't locked out of its own dashboard/
    reports if one admin becomes unavailable and nobody else knows their
    credentials.
  - `updateUser`: same role choice now available on **edit**, so an existing
    staff member can be promoted (or an admin demoted) after the fact — but
    a caller is blocked from changing **their own** role (mirrors the
    existing "nobody can delete their own account" guard in
    `policies/userPolicy.js`'s `destroy()`, same reasoning: prevents a
    company being left with zero admins by a single self-demotion).
  - `updateUser` also strips `is_active` from the request body when the
    target user is the caller themselves — self-deactivation is blocked for
    the same reason.

**PDF receipt fixes (`utils/bookingPdfGenerator.js`, the generator behind the
"Resit Deposit/Deposit Receipt" download button and `BOOKING DEPOSIT
RECEIPT` PDF — distinct from `utils/receiptActivityPdfGenerator.js`, which
