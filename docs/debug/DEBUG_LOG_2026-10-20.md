## 2. Evening activity bookings shown on the next day

**Symptom (production):** an activity booked for 4 Jan 2026, 6:54 PM
(#2881) was marked on **5 Jan** in the booking calendar; one at 8:57 AM on
1 Jan (#2886) was correct. The detail page showed both correctly. This was the
"still open" item in `DEBUG_LOG_2026-10-04.md` §2.

**Root cause:** the app sends `activity_date` without a timezone
(`"2026-01-04T18:54:00"`). `normalizeNullableDate` used `new Date(...)`, which
uses the **server process's** timezone:
- production (UTC) stored it **as typed**: `2026-01-04 18:54`;
- a Malaysia-time machine (local dev) stored it 8 h earlier (`10:54`) — which
  is why it never reproduced locally.

The frontend detail/edit pages already read `activity_date` "as typed"
(literal string, by design), but a few readers converted it to Malaysia time
and added 8 hours — including the backend's `getBookedDates()` (calendar
dots), via `buildMalaysiaDayBoundary` / `+MALAYSIA_OFFSET_MS`.

**How it was confirmed:**
```sh
TZ=UTC               node -e 'console.log(new Date("2026-01-04T18:54:00").toISOString())'  # 18:54Z
TZ=Asia/Kuala_Lumpur node -e 'console.log(new Date("2026-01-04T18:54:00").toISOString())'  # 10:54Z
```

**Fix — `activity_date` means "Malaysia date/time as typed", stored in the
UTC fields, on every server:**
- `utils/normalizers.js`: new `normalizeWallClockDate()` — a date/time with no
  timezone is read as UTC wall-clock (`…T18:54:00` → `…T18:54:00.000Z`) on any
  server; values with `Z`/`+08:00` are kept as given.
- `services/bookingsService.js`: `normalizeActivityDateTime()` uses it (create
  and update); `getBookedDates()` takes the activity date's UTC day (query
  bounds `…T00:00:00.000Z`–`…T23:59:59.999Z`) — no +8 h.
- `utils/bookingPdfGenerator.js`: `formatActivityDate()` uses UTC getters.
- Reminder SQL `DATE(activity_date)` was already correct.

**No data change needed:** production (UTC) has always stored it as typed.
Local dev data created before the fix is 8 h off (dev only).

**Rule for new code:** never `new Date(activity_date)` then read local
hours/date. Take the date/time from the value directly (UTC parts / string).
`created_at` / `receipt_created_at` are real instants and still need
Malaysia-time handling.

**Testing:** 10 new unit tests (`tests/unit/utils/normalizers.test.js`); full
suite 252 → 262 pass. End-to-end, "4 Jan 2026 6:54 PM" through the dev server
(Malaysia time) **and** a copy running with `TZ=UTC` (like production): both
store `2026-01-04 18:54`, booked-dates returns `["2026-01-04"]`; in the
browser the calendar marks only the 4th, list shows 04-01-2026, detail shows
04/01/2026 06:54 PM — 10/10.
