## 1. Database backup (new)

**Why:** another project lost its database and had no backup. RuTEC production had
none either (only manual dumps and `bk_*` tables in the same database).

**Step-by-step of what was done, A to L:** [`../DATABASE_BACKUP_SETUP_STEPS.md`](../DATABASE_BACKUP_SETUP_STEPS.md).

**What was built** (details: [`../DATABASE_BACKUP.md`](../DATABASE_BACKUP.md),
install/restore: [`../../scripts/backup/README.md`](../../scripts/backup/README.md)):

- `scripts/backup/backup-db.sh` — daily `mysqldump`, checked complete, saved in
  `~/st_rural_tourism/rutec-backup/db/`, then encrypted (`rclone crypt`) and
  uploaded to Cloudflare R2. A `.uploaded` marker is written next to each file.
- `cleanup-old-backups.sh` — deletes local backups older than 7 days; never the
  newest 3; a backup that never reached R2 is deleted too, with a Slack alert.
- `predeploy-backup.sh` — called by `.github/workflows/cd-deploy.yml` before pull
  and migrations; **the deploy stops if it fails or is missing**. Keeps the last 5
  in `db/predeploy/`.
- `restore-from-r2.sh` — `list` / `get latest|<name>`: download, decrypt, verify.
- `lib.sh` (shared dump checks, Slack cards, R2/rclone), config template,
  crontab example, `.gitattributes` (LF for `*.sh`).
- Slack: cards in the `#deployments` style through the existing webhook.

**Decided with the senior dev:** daily only; 7 days local; R2 daily, 30 days;
folder inside the app folder; `rclone crypt`; newest 3 never deleted; staging is
not backed up; SSH access for the senior dev, management and Fadzyll.

**Cloudflare R2:** bucket `rutec-db-backups` (Automatic location, Standard),
lifecycle rule `delete-after-30-days`, bucket lock `keep-30-days`, API token
limited to the bucket (Object Read & Write). Keys and the encryption password
are **not** in git; they are in `~/.config/rutec-backup/backup.env` (chmod 600) on
the server and must also be in the team password manager.

**Server facts:** user `stadmin`, MySQL 8.0.45 (`log_bin` ON), database
`rural_tourism` 102.6 MB (dump about 67 MB compressed), 65 GB disk free, clock in
UTC, crontab already had other projects' jobs.

**Installed on the server:** scripts in `~/st_rural_tourism/rutec-backup/scripts/`;
cron `0 19 * * *` backup (03:00 Malaysia) and `30 19 * * *` cleanup (UTC).
`~/docker-prune.sh` was checked: it does not use `--volumes`.

**Tests**
- Fake `docker` stand-in: 45 checks pass (upload, R2 down and retry, cleanup rules,
  Slack JSON, restore, pre-deploy).
- Real server, 2026-11-03: 67 MB dump uploaded to R2 in 21 s; listed;
  downloaded and decrypted; checked as a complete dump; `predeploy-backup.sh`
  7 s; Slack test card appeared in `#deployments`.

**Not verified yet:** the first automatic 03:00 run; a real import into a scratch

## 2. Notes / gotchas

- The server clock is UTC, so cron times **and backup file names** are in UTC.
- Files in R2 get a `.bin` suffix (crypt with readable names).
- The Slack webhook belongs to another Slack app (shows as "ST Intent Harvest"),
  so cards are sent under that sender name; the Server field says
  `rutec-production`.
- `docker-prune.sh` (Sundays 02:00 UTC) removes unused images, including the
  rclone image; the next backup pulls it again (a few seconds).
- GitHub secrets can't be read back, so the Slack webhook URL has to come from
  Slack, not from GitHub.
