## 1. Login sessions: 30 days, re-checked on every request

**Request:** operators should stay logged in unless they press Log Out, and
forgetful users need "Remember me" (frontend log §11).

**Problems with the old design:**
- The token lasted a fixed **24 hours** from login and was never renewed, so
  everyone was logged out daily — and an operator offline for more than a day
  had queued bookings that could not sync until they logged in again.
- `middleware/auth.js` trusted the token completely: role, permissions and
  company were read from the token, never from the database. Deactivation was
  only checked at **login** (`authService.assertAccountIsLoginEligible`), so a
  deactivated user kept working until their token expired. Role changes and
  company moves (e.g. the 110 → 128 merge in §3) only applied after the user
  logged in again.
- Simply making the token long-lived would have made all of the above
  permanent (a JWT cannot be cancelled).

**Decision (after comparing with refresh tokens):** one token lasting 30 days,
renewed while in use, plus a database check on every request. Refresh tokens
were rejected as more work (new table, rotation, grace period for weak rural
signal) for a feature RuTEC doesn't need (logging out a single device —
deactivating the user covers a lost phone).

**What changed:**
| Part | File(s) |
|---|---|
| Token lifetime `JWT_EXPIRES_IN` default `30d` (`getTokenTtl()`) | `middleware/auth.js`, `.env.example` |
| Token records which table its user lives in (`src`: `users` / `tourist_users` / `association_users`) and, for `users`, the password version (`tv`) | `services/authService.js` (both login paths) |
| Per-request check: user exists and is active, `tv` matches; current role, permissions, company and association replace the token's claims | `services/sessionService.js` (new), `middleware/auth.js` |
| Role → permission lookup cached 60 s (one PK query per request otherwise) | `services/sessionService.js` |
| `GET /api/auth/me` returns `data.token` (fresh 30 days) when the current token has < 7 days left | `authService.renewTokenIfNeeded()`, `controllers/authController.js` |
| `users.token_version`, bumped on every password change → other devices logged out | migration `20261009090000-add-token-version-to-users.js`, `models/unifiedUserModel.js` |
| Bumped by: change password (returns the new token as `data.token` for the current device), forgot-password reset, admin setting a password in User Management (`PUT /users/:id`) | `authService.changePassword()`, `passwordResetService.resetPassword()`, `userService.updateUser()` |
| 401 responses now carry a `code` | `middleware/auth.js`, `services/errors/AppError.js` (`SessionInvalidError`) |

**401 codes (the app picks its logout message from these):**
| `code` | Meaning |
|---|---|
| `NO_TOKEN` | No `Authorization` header |
| `INVALID_TOKEN` | Bad signature / malformed |
| `TOKEN_EXPIRED` | Older than 30 days without renewal |
| `ACCOUNT_DEACTIVATED` | `is_active = false` |
| `ACCOUNT_NOT_FOUND` | User row deleted |
| `SESSION_REVOKED` | Password changed since this token was issued |

**Deploy compatibility:** tokens issued before this change have no `src`, so
the middleware keeps the old token-only behaviour for them (they expire within
24 hours). `/auth/me` upgrades an **operator's** old token to a 30-day one
(after checking the account is active), so nobody is logged out by the deploy.
Old tourist/association tokens just expire.

**Gotchas:**
- **`.env` changes need a restart.** dotenv reads `.env` once at start-up, and
  nodemon does not watch `.env`. During testing the local dev server kept
  issuing 24-hour tokens after `.env` was changed to `30d`, until it was
  restarted. Same on staging/production.
- `sessionService` is required **lazily** inside `authenticate`, and it requires
  `authService` lazily too: `authService` imports `middleware/auth`
  (`generateToken`), so top-level requires would be circular.
- `authenticate` is now `async`, but tokens without `src` still call `next()`
  synchronously — the existing route tests (which sign tokens without `src`)
  rely on that.
- Unit tests that mock `middleware/auth` must also provide `getTokenTtl`, and
  tests that load `authService` with mocked models must mock
  `models/associations` (it calls `belongsTo` on the real models).

**Testing:**
- Unit: 186/186 pass (19 new: `tests/unit/services/sessionService.test.js`,
  `tests/unit/services/authService.session.test.js`, new cases in
  `tests/unit/middleware/auth.test.js`).
- Migration: up → down → up on local MySQL (169 users, all `token_version = 0`).
- End-to-end against a real API + local MySQL (temporary user, deleted after):
  30-day token, role change and company move apply without re-login,
  deactivated user refused on every endpoint and at login, reactivation works,
  password change logs out the other device, renewal at < 7 days, old 24h token
  upgraded, expired token → `TOKEN_EXPIRED` — 17/17.
- Long offline periods, tested through the frontend against this backend
  (tokens signed with an `iat` 25 / 31 days in the past): a 25-day-old token
  still works and is renewed to 30 days on reconnect; a 31-day-old token gets
  `TOKEN_EXPIRED`, nothing is created with it, and the queued booking is
  created once after logging in again — 14/14.
- Other browser tests of the frontend against this backend: see the frontend
  log.

**Deploy:** `npx sequelize-cli db:migrate`, set `JWT_EXPIRES_IN=30d` (or remove
it), confirm `JWT_SECRET` is a real secret (the code still falls back to
`"your_jwt_secret"` if it is missing — more important now tokens live 30
days), then **restart**.

## 2. Same offline booking sent twice on reconnect (frontend bug, backend view)

**Symptom:** after reconnecting, an offline booking could end up marked
"Validation error" / failed in the app although it existed on the server
(operators had reported "duplicate" oddities with offline bookings).

**Root cause:** the app started two syncs at the same moment (frontend log
§10), so `POST /api/bookings` arrived twice with the same `idempotency_key`.
`bookingsService` checks for an existing booking with that key before inserting
— which handles **repeated** sends — but two **simultaneous** requests both pass
the check; the second insert then hits the unique index and returns 500 with
the message `"Validation error"` (a `SequelizeUniqueConstraintError`).

**Why no customer was double-booked:** `bookings_idempotency_key_unique` exists
(migration `20260513000001`). That migration passes `where: idempotency_key IS
NOT NULL`, which MySQL ignores (see `CLAUDE.md`) — the result is a full unique
index, which is still correct because NULLs never collide in a MySQL unique
index. Checked locally: no duplicate app bookings; the only near-identical rows
are KTA migration records (copied timestamps, no tourist name).

**Fix:** in the app (one sync at a time). **Possible follow-up:** catch the
unique-constraint error on `idempotency_key` in `createUnifiedBooking` and
return the existing booking, so even simultaneous requests are idempotent.

**Query to check production for real duplicates** (same company, tourist,
product, dates and price, created within 2 minutes; skips KTA migration rows):
```sql
SELECT company_id, tourist_full_name, product_id, booking_type,
       activity_date, check_in_date, total_price,
       COUNT(*) AS copies, GROUP_CONCAT(id ORDER BY id) AS booking_ids,
       DATE_ADD(MIN(created_at), INTERVAL 8 HOUR) AS first_created_malaysia
FROM bookings
WHERE created_at >= '2026-05-01'
  AND legacy_receipt_id IS NULL
  AND status NOT IN ('cancelled')
GROUP BY company_id, tourist_full_name, product_id, booking_type,
         activity_date, check_in_date, total_price
HAVING copies > 1
   AND TIMESTAMPDIFF(SECOND, MIN(created_at), MAX(created_at)) < 120
ORDER BY first_created_malaysia DESC;
```
Rows here are not automatically wrong — a group booked one person at a time
looks the same.

## 3. Manual data operations (DBeaver)

Recorded in `docs/SQL_OPERATIONS_2026-10-08.md`: booking totals since 1 Oct
for a company, listing KTA bookings created on 1 Oct, deleting 8 bookings by
ID (with backup tables), and merging company 110 into 128 (products, bookings,
package legs, users, `legacy_id_map`). A 115 → 158 merge was prepared with the
same steps.

**Lessons:**
- **DBeaver Ctrl+Enter runs the selection as one statement**, so a multi-
  statement block fails with `SQL Error [1064] ... near 'DELETE FROM ...'`
  (nothing runs). Use **Alt+X** (Execute Script), or Manual commit mode.
- Stored times are **UTC**: Malaysia 1 Oct 00:00 is `'2026-09-30 16:00:00'`.
- KTA is linked through `users.association_id = 7`; `companies` has no
  association column.
- Deleting a company **cascades to its products** — leave a merged company
  empty for a while before deleting it.
- After the 110 → 128 merge, company 128 showed **3 users where 2 were
  expected**. Still to be explained (most likely a user added in between).
