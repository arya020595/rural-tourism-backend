## 1. Association bell: "new registration awaiting approval"

**Goal:** association users get a bell like operators and admins, telling them a new
operator registration needs their approval; tapping it opens the Registration
Approvals page.

**What already existed** (registration approval work, 2026-11-02):
- `registrationService.notifyApprovers` creates a `registration_pending`
  notification for every active user of the operator's association and every
  superadmin when an operator registers.
- The frontend bell and panel are on the association dashboard, statistics and
  registrations pages; a `registration_pending` item opens `/association/registrations`.

**Why it didn't work on staging/production:** the bell's endpoints
(`/api/notifications/operator/:id`, `/unread-count`, `/read-all`, `/:id/read`)
required `booking:read`. The association role there only has `bi_dashboard:read`,
`registration:approve` and `association:read`, so every bell call returned 403 and
the bell stayed empty. Locally the association role still has the old full
permission set (including `booking:read`), so it worked in development.

**Fix:** `routes/notificationRoutes.js` accepts `booking:read` **or**
`registration:approve` for the four read routes (`NOTIFICATION_READERS`). The owner
checks are unchanged: everyone still only sees and marks their own notifications.
Creating notifications (`POST /api/notifications`) still needs `booking:update`.

**Test:** `tests/unit/routes/notificationRoutes.test.js` (6 tests): association
approver can list, count, mark all read and mark one read; can't read or mark
someone else's; operators still work; a user with neither permission gets 403.
Against the old routes the three association tests fail; with the fix all pass.

**Frontend (same day):** bell added to the association Account Settings page, so it
is on every association page.

**After deploy:** association users should log out and in again; a new operator
registration then shows a red badge on the bell.
