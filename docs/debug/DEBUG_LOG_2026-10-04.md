## 1. Unit tests failing (500 instead of 201/409) after the operator_admin role feature

**Symptom:** `tests/unit/routes/userCrudRbac.test.js` — `POST /api/users`
returned 500 for "should return 201 and created user" and "should return 409
for duplicate username/email".

**Root cause:** `controllers/userController.js#createUser` was changed to call
the new `userService.getOperatorRoleIdByName(role)`. The test mocks the whole
`services/userService` module and only defined the old
`getOperatorStaffRoleId`, so the controller called `undefined(...)` → 500.

**Fix:** added `getOperatorRoleIdByName` to the mock, switched the three
`POST /api/users` tests to it, and asserted it's called with
`"operator_staff"` (the default when no role is sent).

**Lesson:** when a controller starts calling a new service method, search the
tests for `jest.mock` of that service — module mocks don't fail loudly, they
turn into 500s.

## 2. "Today" receipt list empty, then the fix only worked on the dev machine (timezone)

**Symptom (part 1):** Dashboard → Today showed chart totals for today, but the
Receipt List under it said "No data available". Reproduced locally and on
staging. Trend mode worked.

**Root cause (part 1):** the receipt list and the charts are two different
queries. The list uses `bookingsService.parseDateRangeFilter()`, which built
the day as `${date}T00:00:00.000Z` → `${date}T23:59:59.999Z` — a **UTC** day.
Malaysia is UTC+8, so anything created between Malaysia midnight and 8am has a
UTC timestamp still on the previous day and fell outside the window. Trend
uses whole months, so the 8-hour daily gap was invisible there.

**Symptom (part 2):** after the first fix was deployed, staging's Dashboard
showed "As of: 2026-09-30" on 1 October.

**Root cause (part 2):** the first fix used the local `Date` constructor /
`setHours()`, which follow the **Node process's own timezone**. The dev
machine runs with `TZ=Asia/Kuala_Lumpur`, but staging/production run in UTC,
so the same code behaved correctly locally and wrongly on the servers. The
pre-existing `dashboardService.resolveTodayRange()` had the same problem
(`asOfDate`, today's chart window).

**How it was confirmed:** run the same code under both timezones:
```sh
TZ=UTC node -e "console.log(require('./services/dashboardService').resolveTodayRange().asOfDate)"
TZ=Asia/Kuala_Lumpur node -e "console.log(require('./services/dashboardService').resolveTodayRange().asOfDate)"
```
Before the fix these disagreed between Malaysia midnight and 8am.

**Fix:** compute Malaysia-local days from a hard-coded UTC+8 offset (Malaysia
has no daylight saving), independent of the server TZ:
- `services/bookingsService.js` — `buildMalaysiaDayBoundary()` used by
  `parseDateRangeFilter()` (receipt list, package list date filters).
- `services/dashboardService.js` — `resolveTodayRange()` (Today tab + "As of").
- `services/bookingReminderService.js` — `findUpcomingBookings()`.

**Found by the follow-up audit — booking reminders sent a day early:** the
daily reminder cron (`scripts/bookingReminderScheduler.js`) correctly fires at
Malaysia midnight via node-cron's `timezone` option, but
`findUpcomingBookings()` then did `new Date().setDate(getDate() + 3)` in the
process timezone. On a UTC server at Malaysia midnight (= 16:00 UTC the day
before) it queried **Oct 4 instead of Oct 5**. Simulated with a mocked clock
under `TZ=UTC`; fixed with the same UTC+8 approach.

**Audit — checked and left alone:** `resolveTrendRange()` / `buildUtcDate()`
(explicit YYYY-MM input, already UTC-pure); `operatorActivityService
.matchesDateFilter()` (both sides of its comparison use the same process TZ);
password-reset token expiry (pure duration); statement "generated on" label,
`currentYear` validation and company `establishedYear` (cosmetic, only off
within hours of a boundary); frontend `setHours()` (runs in the user's own
Malaysian browser).

**Still open — please verify on staging:** `bookings.activity_date` is sent by
the frontend without a timezone (e.g. `2026-09-30T18:14:00`) and parsed with
the server's TZ. Locally that stores 10:14Z (correct); on a UTC server it
stores 18:14Z, which is 02:14 the next day in Malaysia. Evening activity
bookings created on staging/production may display (and get booking-calendar
dots) on the wrong day. Not changed yet because it affects stored data — make
a 7pm booking on staging and check where it lands.

## 4. Company profile save → 500 "Validation error"

**Symptom:** `PUT /api/companies/59` from Company Profile returned 500 with
the message "Validation error".

**Root cause:** `companyService.updateCompanyOwner()` bulk-updated **every**
`operator_admin` of the company with the owner name/email. Since operator
admins can now add co-admins, company 59 had two admins (Justin 139, Fadzil
173); setting both emails to `justinranny@gmail.com` broke the unique email
constraint (`SequelizeUniqueConstraintError`, whose message is literally
"Validation error"). If the emails hadn't collided, the save would silently
have renamed the co-admin too.

**How it was confirmed:** ran the bulk update inside a transaction that was
rolled back, printing `e.errors` → `email must be unique`.

**Fix:**
- `companyService.getCompanyOwner()` — the single source of truth for "the
  owner" (first operator_admin by id). Used by both display
  (`userService.getUserById` → `owner_user_id`, `owner_full_name`,
  `owner_email`) and update.
- `updateCompanyOwner()` updates that one row only; a duplicate email now
  returns a 409 "This email is already used by another account."
- `companyController.updateCompany()` ignores owner name/email unless the
  caller **is** the owner (or superadmin). Co-admins can still edit company
  details. Covered by two new tests in `tests/unit/routes/companyCrud.test.js`.

**Related frontend bug:** the profile's Email field showed the *logged-in*
user's email, not the owner's, so a co-admin saving the form would have sent
their own email onto the owner's account. See the frontend log.

**Known limitation:** company details are saved before the owner fields, so a
409 on the email still leaves the company changes saved. Wrapping both in one
transaction would fix that if needed.

## 5. New endpoint for the booking calendar dots

`GET /api/bookings/booked-dates?from=YYYY-MM-DD&to=YYYY-MM-DD`
(`authorize("booking:read")`, scoped by the booking policy to the caller's
company). Returns the Malaysia-local dates in the range that have at least one
non-cancelled/non-rejected booking: activity/package bookings on their
activity date, accommodation bookings on every day from check-in to check-out.
Range capped at 400 days; bad input → 400. Implemented in
`bookingsService.getBookedDates()`. The existing booking list couldn't be
reused — its date filter is on receipt/created date, not activity/stay date.

## 6. Deposits couldn't hold cents (RM3.50)

**Symptom:** operators need prices like RM3.50. Total already worked
server-side (`total_price` is `DECIMAL(12,2)`), but deposits were whole
numbers at every layer.

**Fix:**
- `migrations/20261003120500-change-total-deposit-to-decimal.js` —
  `bookings.total_deposit` INTEGER → `DECIMAL(12,2)`. Lossless for existing
  rows (local: 29 deposits, sum 515883 → 515883.00).
- `models/bookingModel.js`, `validators/bookingValidator.js`,
  `services/bookingsService.js` — accept numeric ≥ 0, rounded to 2 decimals
  (`roundMoney()`).

**Gotcha:** MySQL returns `DECIMAL` columns as strings (`"120.00"`). Every
current reader already wraps the value in `Number(...)`, so nothing broke —
keep doing that for new code.

**Deploy:** run `npx sequelize-cli db:migrate` on staging/production first.
